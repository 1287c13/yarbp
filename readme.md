## Общее описание

**ЯРБП** (Язык Разметки для Быстрого Прототипирования, он же YARBP -
"Yet Another Rapid Business Prototyping") - это язык разметки для
аналитиков, который легко писать и читать. Сверхкомпактный, русскоязычный,
человекочитаемый DSL.
Его главная задача - служить единым, простым источником истины,
из которого можно автоматически сгенерировать что угодно: от макета интерфейса и схемы BPMN до JSON-конфига, Protobuf и XML.

<a id="ideas"></a>

### Идеи:
- Удобство набора (в том числе при работе в русской раскладке)
- Один синтаксис -> одно AST -> множество целевых представлений:
  - разметка: JSON / XML / Protobuf
  - макеты UI
  - BPMN схемы
  - ...
- Широкий набор фич для максимально гибкой разметки целевых сущностей:
  - типизация
  - макросы
  - комментарии
  - директивы конвертера
  - настраиваемый сахар для объявления свойств
- Вся семантика на стороне конвертера - язык определяет только структуру, а смысл придаёт целевой конвертер.
- При этом низкий порог входа. Хотим писать просто - пишем просто, разметка валидна. Хотим писать компактно и удобно - изучаем фичи.

## Спецификация

<a id="syntax"></a>

### Синтаксис

<a id="advanced-example"></a>

#### Расширенный пример

```yarbp
! as json
:
  .order_id 12345
  .status "new"
  .is_active yes
  :client .first_name Jack .last_name White .id '54312'
  ..items
    : .sku ART-001 .price 1299.99
```

Лидирующие символы указывают на тип ключа.
В предыдущем примере типы ключей выводились автоматически, но их можно указывать явно.
Доступные типы ключей:

| Префикс | Тип ключа |
| :---: | --- |
| `.` | лидирующая точка -> ключ примитивного значения (атрибут объекта) |
| `:` | лидирующее двоеточие -> ключ объекта |
| `..` | лидирующая двойная точка -> ключ массива |

Указание типа ключа без значения ключа объявляет анонимное значение (значение без имени),
см. ниже как сконвертировалось в этом примере корневой объект и объект внутри "items"

Рендер:

```json
{
  "order_id": 12345,
  "status": "new",
  "is_active": true,
  "client": {
    "first_name": "Jack",
    "last_name": "White",
    "id": "54312"
  },
  "items": [
    {
      "sku": "ART-001",
      "price": 1299.99
    }
  ]
}
```

<a id="typed-comments"></a>

#### Пример с типизацей и комментариями

```yarbp
! as proto
Order
  .order_number:string --- comment
  .date:string --- comment
  ..items
    Product .name:string
      .size:enum UNSPECIFIED SMALL MEDIUM LARGE
    .position:int32
```

ЯРБП поддерживает комментарии и типизацию значений.
Типы указываются после ключей через двоеточие как ```ключ:тип```.

Комментарии начинаются с ```---```.

Рендер:

```proto
message Order {
  string order_number = 1;  // comment
  string date = 2;          // comment
  repeated Item items = 3;
}

message Product {
  string name = 1;
  Size size = 2;
}

message Item {
  Product Product = 1;
  int32 position = 2;
}

enum Size {
  UNSPECIFIED = 0;
  SMALL = 1;
  MEDIUM = 2;
  LARGE = 3;
}
```

<a id="macros"></a>

#### Макросы.

Макросы в ЯРБП объявляются лидирующим ```@```. Используются для того чтобы минимизировать написание повторяющегося кода.
Раскрываются на уровне парсера подстановкой, т.о конвертору макросы уже недоступны, AST подается раскрытым.

Определение задаётся как `@a`. Вызов: `имя(a)` — в скобках имя макроса, перед скобками имя результата. `xx(a)` раскроется в узел `xx`, `yy(a)` — в `yy`. Вызов без скобок (`a`) оставляет имя `a`. Пробелы внутри `имя(a)` не допускаются: вызов должен быть одним токеном, иначе разметка ломается.

Пример:

```yarbp
! as xml

@item
  .id item-(( item-number ))
  ..content
    (( variable-content ))
    extra-content .prop-1 (( prop-1 )) .prop-2 (( prop-2 ))
  controller .name controller-(( item-number ))

items
  item .item-number 1 .prop-1 1 .prop-2 2
    ..variable-content
      sub-item .id 1
  item .item-number 2 .prop-1 3 .prop-2 4
    ..variable-content
      sub-item .id 1
      sub-item .id 2
  item .item-number 3 .prop-1 5 .prop-2 6
    ..variable-content
```

Рендер:

```xml
<items>
  <item id="item-1">
    <content>
      <sub-item id="1"/>
      <extra-content prop-1="1" prop-2="2"/>
    </content>
    <controller name="controller-1"/>
  </item>
  <item id="item-2">
    <content>
      <sub-item id="1"/>
      <sub-item id="2"/>
      <extra-content prop-1="3" prop-2="4"/>
    </content>
    <controller name="controller-2"/>
  </item>
  <item id="item-3">
    <content>
      <extra-content prop-1="5" prop-2="6"/>
    </content>
    <controller name="controller-3"/>
  </item>
</items>
```

<a id="substitution"></a>

#### Подстановка по ключу нулевого уровня

Вне макроса `(( имя ))` означает «подставь сюда содержимое ключа `имя` с нулевым
отступом». Ключ-источник убирается из вывода: он нужен только для подстановки.
Если имя встречается несколько раз, подстановка выполняется во всех местах, а
ключ удаляется один раз.

```yarbp
а .б (( с ))
.с д
```

Эквивалентно:

```yarbp
а .б д
```

- если ключа с таким именем нет, `(( имя ))` остаётся как есть, а в строке
  статуса появляется диагностика «нет ключа для подстановки»;
- объект или массив подставляется содержимым: дети переходят в целевой узел;
  внутри строки допустимы только примитивы и фрагменты кода;
- макросы работают как раньше: в теле `@...` имя резолвится из аргументов
  вызова, а не из ключей документа.

<a id="code-block"></a>

#### Фрагмент кода

Фрагмент кода — лексический остров: между открывающим и закрывающим fence
текст не парсится, отступы сохраняются. Допустимы тройной и одинарный
обратный апостроф; язык опционален и берётся из первого слова после
открывающего fence.

````yarbp
.обработчик-1
```bsl
// Комментарий
Процедура Тест()
КонецПроцедуры
```

.обработчик-2
`js
function test() { return 1; }
`
````

В AST это примитив:

```json
{
  "nodeType": "MEANING",
  "key": "обработчик-1",
  "prefix": ".",
  "valueType": "CODE",
  "language": "bsl",
  "value": "// Комментарий\nПроцедура Тест()\nКонецПроцедуры"
}
```

- без языка `language` равен `null`, встроенная подсветка не запускается;
- отступ самого fence снимается с содержимого, внутренние отступы кода
  сохраняются относительно fence; табы внутри острова не нормализуются;
- фрагмент можно передать параметром макроса;
- внутри фрагмента кода меню автодополнения ЯРБП не вызывается (включая Alt):
  это чужой язык;
- незакрытый блок — ошибка «незакрытый фрагмент кода».

Подсветка содержимого встроенных языков (BSL/1С, JS/TS, SQL, JSON) выполняется
отдельным отложенным проходом через 150 мс после подсветки ЯРБП. Границы и
язык рисует основной хайлайтер; проход меняет только содержимое блока, поэтому
курсор и выделение не сбиваются. Без языка проход не запускается.

Содержимое BSL/1С красится в традиционную схему конфигуратора 1С: ключевые
слова и операторы — красные, идентификаторы — синие, строки/числа/даты —
чёрные, комментарии — зелёные, препроцессор и аннотации — коричневые. Точные
цвета и источник — `src/js/classes/highlighters/README.md`.

<a id="next-line-value"></a>

#### Значение с новой строки

Значение примитивного ключа можно записать на следующей строке:

````yarbp
а .б (( с ))
.с
"
Многострочный
Текст
"
````

Эквивалентно:

````yarbp
а .б (( с ))
.с "Многострочный
Текст"
````

Работают строки в любых кавычках, многострочные строки, фрагмент кода, число,
`yes`/`no`/`да`/`нет`, `null`. Bareword на следующей строке остаётся новым
узлом, а не значением. Если значения нет, AST сохраняет прежнее пустое значение
для совместимости, но в строке статуса появляется диагностика «ожидалось
значение». Позиция значения в AST указывает на строку значения, а не на ключ.

<a id="sugar-ast"></a>

#### Сахар и дизайн AST.

Также существует специальный узел "shorthand", использующийся для сокращенного объявления свойств.
Для объявления сахара после имени объекта записывается знак равно.

Сахар может интерпретироваться конвертерами по их усмотрению (см. пример с динамической типизацией сахара в "Прикладной пример").

Пример

```yarbp
! как аст
поле-формы:дата = Дата начала
```

Рендер

```json
{
  "nodeType": "ROOT",
  "directives": [
    {
      "nodeType": "DIRECTIVE",
      "value": "как аст",
      "prefix": "!",
      "position": {
        "start": 0,
        "end": 9
      }
    }
  ],
  "children": [
    {
      "nodeType": "MEANING",
      "key": "поле-формы",
      "valueType": "OBJECT",
      "prefix": "",
      "position": {
        "start": 10,
        "end": 20
      },
      "type": "дата",
      "children": [
        {
          "nodeType": "MEANING",
          "key": "shorthand",
          "prefix": ".",
          "position": {
            "start": 27,
            "end": 40
          },
          "valueType": "STRING",
          "value": "= Дата начала"
        }
      ]
    }
  ]
}
```

В этом примере разметка сконвертирована не в прикладное представление, а в AST для демонстрации дизайна AST.

<a id="xpm"></a>

#### Рендер карты процесса-опыта (КПО)

Один из конвертеров ЯРБП превращает текстовое описание бизнес-процесса
в визуальную **карту процесса-опыта**: дорожки, участники, ключевые точки,
события, таблицы решений и связи между ними.

> **Карта процесса-опыта** - метод визуализации любого хозяйственного процесса
> с акцентом на человеке, но при этом с учётом обеспечивающих его
> технических аспектов. Схема согласует пользовательский опыт и бизнес-процессы
> в единой многослойной карте: акторы и агенты, ключевые точки, линии тока,
> линии взаимодействий, триггеры, события и аннотационные блоки.
>
> - [Описание метода](https://ashapiro.ru/xpm) · [База знаний на GitHub](https://github.com/Byndyusoft/xp-mapping)

Пример разметки:

```yarbp
! как КПО

дорожка

  разделитель = ЭТАП 1
  событие = Событие А
  пусто
  пусто
  разделитель = ЭТАП 2
  событие = Событие Б

участник = Актор 1 .картинка женщина-яркая-одежда

  точка = Ключевая точка 1
    ..связи ->
    ..аннотации
      Каналы, артефакты,
      барьеры, средства,
      действия, вход и выход

  точка
    .ид триггер-1-2
    .тип -<>
    таблица-решений
      ..шапка "Параметр А" "Параметр Б"
      ..правила
        :
          ..параметры "Значение А1" "Значение Б1"
          .результат точка-1-4
        :
          ..параметры "Значение А2" "Значение Б2"
          .результат точка-2-4
        :
          ..параметры "Значение А3" "Значение Б1"
          .результат точка-2-3
        :
          ..параметры "Значение А4" "Значение Б2"
          .результат точка-2-3

  пусто

  точка = Триггер сработал?
    .ид точка-1-4
    .тип -<>
    ..связи [да]-> нет нет [нет]->триггер-1-2

  точка = 5
    появление .аннотация + Актор 3, Актор 4
      ..участники
        участник .картинка производство
        участник .картинка оператор
    ..связи -> <..

участник = Актор 2 .картинка мужчина-менеджер

    пусто

    пусто

    точка = 2, вне контроля
      .ид точка-2-3
      .тип -о
      ..связи ->

    точка = 3, опциональная
      .тип -(
      .ид точка-2-4
      ..связи -->

    точка = 4
```

#### Прикладной пример

<details>

<summary>Если не готовы погружаться в детали - проходите дальше</summary>

Это целевой пример использования ЯРБП для генератора форм. Используются макросы,
директивы конвертора (рендерера формы) предоставляющие типизацию сахара.

> Как эта разметка превращается в работающую форму и какие действия уже
> поддерживаются: **[Гайд по генератору форм](#ui-generator-guide)**.

Разметка формы:

```yarbp
! как xml
! типизация-сахара(поле)  лэйбл/плейсхолдер/обязательный/постфикс
! типизация-сахара(опция) представление/значение

@ввод-показателей
  группа:плитка =     (( имя-формы ))
    .направление вертикально
    табы .ид          (( ид-табов ))
      таб#список
                      (( контент-списка ))
        кнопка =    + (( имя-кнопки-добавления ))
          .навигация #(( ид-табов )).добавить
      таб#добавить
        группа:плитка
          ..доп-функционал очистить
          надпись =   (( имя-добавляемой-сущности ))

<a id="ui-generator-guide"></a>

#### Гайд по генератору форм

Форма не пишется вручную в HTML: она собирается из ЯРБП-разметки. Цепочка
такая:

```text
ЯРБП-разметка → лексер → парсер → AST
                             → UIGenerator.generateHTML(ast)  → HTML
                             → UIRuntime.mount(root)          → действия
```

`UIGenerator` отвечает только за разметку. Состояние и поведение формы живут
в `src/js/classes/ui/UIRuntime.js`:

- `UIViewModel` — `activeTab`, значения полей и строки списков;
- `UIRuntime` — делегированные обработчики, навигация, очистка, проверки,
  диалоги и переносы `.источник` → `.приемник`.

В редакторе runtime подключается как обычный ES-модуль. В standalone-выгрузке
его исходник встраивается в тот же HTML, поэтому выгруженная форма остаётся
одним файлом и работает без сети.

##### Минимальная форма

```yarbp
! как форма
форма
  группа:плитка = Заявка
    поле = Имя / Введите имя / да
    поле#количество:число = Количество / / да / шт.
      ..доп-функционал очистить
```

`поле` рисует label, input/select и, при `.доп-функционал очистить`, кнопку
очистки. `required` (третий сегмент сахара или `*`) блокирует добавление
пустой строки. Четвёртый сегмент сахара — `.постфикс` (`шт.`); его можно
задать и атрибутом `.постфикс шт.`.

##### Табы и списки

```yarbp
! как форма
форма
  табы .ид ops
    таб#список
      группа:набор-соответствий
    таб#добавить
      поле#количество:число = Количество
```

У таба есть `data-tab-id` — по нему работают `.навигация`, `.источник` и
`.приемник`. `.ид` задаёт общий id контейнера табов.

##### Кнопки действий

Кнопка рисуется, если у неё есть хотя бы одно действие:

```yarbp
кнопка = Добавить
  .источник #добавить
  .приемник #список
```

```yarbp
кнопка = Назад
  .навигация #ops.список
  .проверить #добавить.количество
  .тип_проверки пусто
  .цель_проверки запретить
  .диалог Заполните количество / Ок
```

| Атрибут | Что делает |
| --- | --- |
| `.источник` | откуда брать значения (таб или контейнер) |
| `.приемник` | куда добавить строку и какой таб открыть |
| `.навигация` | на какой таб перейти; используется последний сегмент `#табы.таб` |
| `.проверить` | поле для проверки перед действием |
| `.тип_проверки пусто` | срабатывает, если поле пустое |
| `.цель_проверки запретить` | не выполнять переход при ошибке |
| `.диалог Текст / Кнопка` | показать модальное окно с причиной |

Если `.диалог` указан без `.проверить`, окно показывается по нажатию.

##### Состояние формы

`UIRuntime` создаёт `UIViewModel` и обновляет её при вводе, смене таба,
переносе строки и очистке. Модель можно получить так:

```js
const runtime = new UIRuntime(root);
runtime.mount();

const state = runtime.getState();
// { activeTab, fields, lists, tables }

runtime.restore(state);
```

Это состояние не зависит от конкретной разметки: его можно сохранить,
передать в 1С или восстановить после перерисовки. Редактор использует те же
`getState()` / `restore()` через `HTMLUIRenderer.captureState()` и
`restoreState()`.

##### Выгрузка standalone

Кнопка «HTML» в UI-макете выгружает **один** HTML-файл:

- разметка собрана из AST;
- `UIRuntime` встроен в страницу как module-скрипт с CSP nonce;
- внешних файлов и сети для работы формы нет;
- действия `.источник`/`.приемник`, диалоги и табы работают так же, как
  в предпросмотре.

Выгрузка асинхронная: `HTMLExporter` читает исходник `UIRuntime.js` и
встраивает его. В редакторе это происходит по кнопке; тест открывает
полученный HTML в iframe и проверяет, что форма ожила.

##### Что уже поддерживается

- `форма`, `группа:плитка` с `.направление`, `поле` (текст, число, дата,
  почта, телефон, выбор), `опция`, `надпись`;
- `.тип-данных` сохраняется в `data-type` поля;
- `табы .ид`, `таб#ид`, навигация по табам;
- `группа:набор-соответствий` как список строк;
- `группа:таблица-соответствий` как редактируемая таблица: колонки из
  полей, добавление/удаление строк, `.постфикс`;
- `кнопка` с `.навигация`, `.источник`/`.приемник`, `.проверить`,
  `.диалог`;
- `.доп-функционал очистить`, required-поля, удаление повторяемой строки.

##### Ограничения

- `кнопка` без действия не рисуется — это осознанно: пустые кнопки не
  создают ложного интерфейса.
- `.тип_проверки` сейчас понимает `пусто`; другие проверки нужно добавлять
  в `UIRuntime.checkAction()`.
- `группа:таблица-соответствий` редактируется, но стартовые строки из
  разметки пока не задаются: формат для массивов/массивов объектов должен
  быть определен отдельно.
- `.тип-данных` пока является метаданными (`data-type`), а не загрузкой
  справочника или динамическим списком значений.

##### Как проверить

```powershell
python tests/features/run_tests.py
python tests/security/run_tests.py
```

`tests/features` проверяет табы, очистку, `.источник`/`.приемник`, диалог
и standalone-выгрузку. `tests/security` проверяет CSP, nonce и отсутствие
`innerHTML` в runtime.

<a id="bpmn"></a>

#### Конвертер BPMN

Конвертер собирает из AST **BPMN 2.0 XML** (`bpmn:definitions` + `bpmndi`).
Результат показывается в панели результата, а кнопка скачивания выгружает
`diagram.bpmn`. Если в документе несколько процессов или есть сообщения/
аннотации, автоматически собирается collaboration с участниками.

Минимальный пример:

```yarbp
! как БПМН

процесс = Приём заказа
  ..роли
    роль .имя Менеджер
    роль .имя Кладовщик

  событие = Заказ получен
    задача = Проверить заказ .роль Менеджер
      шлюз = Товар есть?
        ветка = да
          задача = Зарезервировать .роль Кладовщик
        ветка = нет
          событие = Отказ .расположение конец
    событие .расположение конец
```

Что понимает конвертер:

- `процесс = <имя>` - процесс; несколько процессов объединяются в collaboration;
- `..роли` → `роль .имя <имя>` - дорожки процесса;
- потоковые узлы: `событие`, `задача`, `шлюз`, `подпроцесс`;
- `ветка = <подпись>` - ветка шлюза; подпись ставится на исходящий sequence flow,
  а `+`/`-` - просто текст подписи, не отдельная семантика;
- `задача .тип` - `сервис`, `скрипт`, `пользователь`, `отправка-сообщения`,
  `получение-сообщения`, `бизнес-правило` (по умолчанию `manualTask`);
- `шлюз .тип` - `параллельный` (по умолчанию эксклюзивный);
- `событие .расположение` - `начало`, `промежуточное`, `конец`;
- `повторение` - `параллель`, `последовательно`, `цикл`;
- `.ид` - явный BPMN id; `.роль` - дорожка задачи;
- `процесс .исполняемый да` - исполняемый процесс (`isExecutable="true"`);
- `процесс .пул = <имя>` - имя пула-участника (по умолчанию = имя процесса);
  `процесс .ид = <id>` - явный id процесса (нужен для вызова из другого пула);
- `задача .тип вызов .вызывает = <id процесса>` - `callActivity` с `calledElement`;
- `группа = <имя>` - группа-рамка вокруг задачи (`bpmn:group` + `categoryValue`);
- артефакты задачи (значение после `=`): `комментарий = <текст>`,
  `данные = <имя>` - задача отдаёт данные (`dataOutputAssociation`),
  `данные-вход = <имя>` - задача читает данные (`dataInputAssociation`),
  `данные-выход = <имя>` - то же, что `данные`; `база-данных = <имя>`;
  объект данных один на имя: две задачи с `данные = Товар` дают один
  `dataObject` и две ссылки на него;
- `связь = --> <id>` / `связь = <-- <id>` - message flow;
  по BPMN он идёт **между пулами**: внутри одного пула конвертер предупреждает
  (там нужен обычный поток работ);
- `.х`, `.у`, `.ш`, `.в` и `.х-закр`, `.у-закр` - явные координаты;
  остальное раскладывается автоматически.

<a id="openapi"></a>

#### Конвертер OpenAPI (openapi)

Тот же документ может описывать не только процесс, но и **контракт REST API**:
конвертер собирает OpenAPI 3.0.3 в JSON — его открывают Swagger UI, Postman и
генераторы клиентов.

```yarbp
! как openapi
api = Заказы .версия 1.0.0 .описание "API заказов"
  сервер = https://api.example.com/v1
  ..пути
    путь = /orders .описание "Заказы"
      метод = get .операция "Список заказов" .ответ 200 .ответ 500
      метод = post .операция "Создать заказ" .ответ 201 .запрос Заказ .обязательное да
  ..схемы
    схема = Заказ
      поле = id .тип целое .формат int64 .обязательное да
      поле = status .тип строка .значение new .значение paid
      поле = client .тип ссылка:Клиент
```

Что понимает конвертер:

- `api = <название>` - контракт целиком; `.версия`, `.описание`, `.заголовок`;
- `сервер = <url>` - `servers[]`;
- `путь = </адрес>` + `.описание`; внутри - `метод = <get|post|put|delete|…>`;
- у метода: `.операция` (summary), `.ответ <код>` (можно несколько),
  `.запрос <имя схемы>` (requestBody со `$ref`), `.обязательное да`, `.тег`;
- `схема = <имя>` + `поле = <имя>`; у поля: `.тип` (`строка`, `целое`, `число`,
  `логическое`, `массив`, `объект`, `ссылка:<Схема>`), `.элемент` (тип элемента
  массива), `.формат`, `.описание`, `.пример`, `.значение` (перечисление),
  `.обязательное да`;
- секции `..пути` и `..схемы` - только для читаемости, конвертеру важен тип узла.

Непонятное не теряется молча: путь без `/`, кривой код ответа, ссылка на
несуществующую схему, неизвестный узел - всё попадает в строку диагностики под
панелью (как в BPMN). Если у метода не указан `.ответ`, подставляется `200`.

**Обратный импорт.** Чужой контракт можно затащить в разметку отдельным
инструментом (не в редакторе — редактор принимает только разметку):

```powershell
python tools/openapi2yarbp.py spec.json                # разметка в stdout
python tools/openapi2yarbp.py spec.json -o case.yarbp   # в файл
python tools/openapi2yarbp.py spec.json --check case.yarbp   # сверить, что не разъехалось
```

Поддерживается то же, что умеет конвертер в обратную сторону (`info`, `servers`,
`paths` с методами/ответами/`requestBody`, `components.schemas`); остальное
(`parameters`, `security`, `oneOf`, тело ответа) печатается предупреждением в
stderr. Круговой рейс `spec → разметка → spec` проверяется тестами
(`tests/openapi2yarbp` + браузерный набор).

<a id="json-schema"></a>

#### Конвертер JSON Schema (схема)

Та же разметка `схема`/`поле`, что у OpenAPI, но на выходе — **JSON Schema**
(draft 2020-12): её понимают валидаторы, редакторы JSON и генераторы типов.
Нужна, когда документ описывает структуру данных, а не эндпоинты.

```yarbp
! как схема
api = Заказ .версия 1.0.0 .описание "Заказ покупателя" .корень Заказ
  ..схемы
    схема = Заказ
      поле = id .тип целое .формат int64 .обязательное да
      поле = client .тип ссылка:Клиент .обязательное да
    схема = Клиент
      поле = name .тип строка .обязательное да
```

Результат:

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "title": "Заказ",
  "description": "Заказ покупателя",
  "$defs": { "Заказ": { "...": "..." }, "Клиент": { "...": "..." } },
  "$ref": "#/$defs/Заказ"
}
```

- `.корень <имя>` выбирает схему, на которую смотрит `$ref` (по умолчанию —
  первая); неизвестное имя — предупреждение и откат на первую;
- `.ид` у `api` становится `$id` (адрес схемы);
- `поле … .тип ссылка:<Схема>` → `$ref: "#/$defs/<Схема>"`;
- `схема` можно писать и прямо в корне документа, без `api`.

Опечатка в атрибуте поля (`.тпи` вместо `.тип`, `.обязателное` вместо
`.обязательное`) — предупреждение в строке диагностики, а не тишина: раньше
такое поле молча становилось строкой и молча переставало быть обязательным.

**Обратный импорт.** Готовую схему (от бэкенда, из генератора типов, из
редактора JSON) тоже можно затащить в разметку — симметрично OpenAPI:

```powershell
python tools/schema2yarbp.py schema.json                 # разметка в stdout
python tools/schema2yarbp.py schema.json -o case.yarbp   # в файл
python tools/schema2yarbp.py schema.json --check case.yarbp   # сверить, что не разъехалось
```

Читаются `$defs` (и старое `definitions` из черновика-07), `properties`,
`required`, `type`/`format`/`enum`/`items`/`$ref`, `title`/`$id`/`description`
корня. Схема без `$defs` (просто объект с `properties`) становится одной схемой
с именем из `title`. Всё, чего разметка не умеет (`oneOf`, `allOf`, `pattern`,
границы чисел, `if/then/else`, поля прямо в корне при наличии `$defs`),
печатается предупреждением в stderr — молча ничего не выбрасывается. Круговой
рейс `schema → разметка → schema` проверяется тестами (`tests/schema2yarbp` +
браузерный набор).

<a id="mermaid"></a>

#### Конвертер Mermaid (мермейд)

Та же разметка процесса, но на выходе — **flowchart Mermaid**: он рендерится
прямо в GitHub/GitLab и в markdown, поэтому схему можно показать в PR текстом,
без картинок и вложений.

````yarbp
! как мермейд
процесс = Отгрузка
  ..роли
    роль .имя Кладовщик
  событие = Начало
    задача = Собрать заказ .роль Кладовщик
    событие .расположение конец
````

Результат:

````mermaid
flowchart LR
  subgraph Process_1["Отгрузка"]
    direction LR
    subgraph Lane_1["Кладовщик"]
      StartEvent_1(["Начало"])
      Activity_1["Собрать заказ"]
      EndEvent_1(("Конец"))
    end
    StartEvent_1 --> Activity_1
    Activity_1 --> EndEvent_1
  end
````

Соответствия: процессы и роли — `subgraph`, подпроцесс — тоже `subgraph`,
задача — прямоугольник, `callActivity` — `[[вызов: …]]`, исключающий шлюз —
ромб, параллельный/инклюзивный — шестиугольник, события — скобки, данные —
`>"…"]`, хранилище — `[("…")]`. Поток работы — стрелка, ветка шлюза — подпись
`-->|"да"|`, условие — пунктир `-.->`, boundary-событие и данные — тоже пунктир.
Поток с условием подписывается `-.->|"да: код = 200"|`, поток «по умолчанию» —
`-.->|"иначе: по умолчанию"|`: по схеме видно, какие ветки решаются выражением,
а какая срабатывает иначе.

Ограничения: группы Mermaid подграфами не выразить (узел живёт в одном
`subgraph`), поэтому они уходят комментариями `%% группа "…": id`.

#### Конвертер ТСД (форма-тсд)

Конвертер собирает из AST **IR формы** - тот же JSON, который читает движок
терминала сбора данных. В редакторе показывается предпросмотр формы в рамке ТСД,
кнопка "JSON" выгружает конфиг `<заголовок>.json`, "HTML" - готовую страницу
`<заголовок>.html` со встроенными CSS, движком и IR, а "мок-сервер" - один
Python-модуль со стандартной библиотекой: хук штрихкода, отправка данных и
health для индикатора сети.

Кнопка "JSON" отдаёт **конфиг для расширения 1С** (`фф_КонфигТСД`): корень
`{type, заголовокФормы, типКлиента, версияКонфига, сервис, watch, обработчики,
children}`, коды обработчиков приезжают парами `код` + `язык` из фрагментов кода
(```` ```bsl ````), а `обработчики` - свойство корня, а не узел `children`.
Контракт целиком - `src/js/classes/renderers/flexforms/README.md` (разделы
«Контракт конфига с расширением 1С» и «Кэш-сервис») и
`kpp/docs/11-tsd-config.md`; ключ доступа кэш-сервиса в конфиг не попадает
(он вводится на странице входа и уходит заголовком `X-Api-Key`).

Минимальный пример:

```yarbp
! как форма-тсд

форма
  .заголовокФормы Отправка данных в 1С
  .сервис http://127.0.0.1:8765/rt_morato_bot/hs/dp
  .ширинаИнтерфейса 309px

  операция = Подобрать товар / a_1
    .имяКнопки Добавить в заказ
    группа .сетка grid-template-columns: repeat(1, 1fr); gap: 10px;
      поле:штрихкод = Штрихкод / a_1_f_1
        .хук /link
        .автофокус да
        ..приемник a_1_f_2 a_1_f_3
      поле:надпись = Товар / a_1_f_2
      поле:число = Кол-во / a_1_f_3
```

`сервис` — базовый адрес в шапке формы. Относительные `.хук`/`.урл`
(`/link`, `/processing`) склеиваются с ним; полные URL с протоколом
используются как есть, а без `сервиса` относительные адреса работают от origin
страницы. Адрес сервера выводится в шапке ТСД.

Что понимает конвертер:

- `форма` - корневой узел; свойства вида `.заголовокФормы`, `.сервис`,
  `.ширинаИнтерфейса`, `.ширинаПоля`, `.ширинаПодписи` и т.п.;
- `операция = <имя> / <id>` - действие с кнопкой; свойства `.имяКнопки`,
  `.очиститьФорму`, `.приемник`, `.заголовокФормы`, `.урл`, `.перезагрузить`;
- `группа` - анонимный контейнер полей/таблиц; `.сетка` задаёт CSS-сетку;
- `поле:<вид> = <подпись> / <id>` - поле; вид задаётся суффиксом ключа
  (`штрихкод`, `выбор`, `надпись`, `число`, …); свойства `.автофокус`,
  `.кнопкаОчистки`, `.хук`, `.поискПо`, `.режимСканирования`, `.вызывать`;
- `..приемник`, `..значенияПриемниковПоУмолчанию`, `..опции` и подобные
  массивные свойства собираются в массивы даже из одного значения;
- `стили` - необязательный узел стилей; без него берутся умолчания схемы.

Подробности и полный пример: `src/js/classes/renderers/flexforms/README.md`,
встроенный пример "Форма ТСД" в редакторе и `tests/flexforms/`.

#### Синтаксис в PEG

````peg
; ============================================================
; ЯРБП v2.0 - PEG спецификация
; ============================================================

документ              <- элемент*
элемент               <- отступ? выражение? комментарий? CRLF
выражение             <- директива / узел+

комментарий           <- префикс-комментария [^\n]*
директива             <- префикс-директивы S? имя-директивы S значение-директивы
узел                  <- сложный-узел / примитивный-узел

сложный-узел          <- объект / массив

объект                <- ( ( префикс-объекта? ключ ) / ( префикс-объекта ключ? ) )
                         ( ":" тип )? ( S+ ( объект / массив / примитивный-узел / shorthand ) )*
массив                <- ( ( префикс-массива? ключ ) / ( префикс-массива ключ? ) )
                         ( ":" тип )? ( S+ ( объект / массив / значение ) )*

shorthand             <- ключ S* "=" S* значение
примитивный-узел      <- префикс-примитива ключ
                         ( " " значение / S* CRLF S* значение )?
примитив              <- строка / число / булево / null
строка                <- ( токен S? )+ / строка-в-кавычках

; --- Семантические определения ---
тип                   <- токен
ключ                  <- токен
имя-директивы         <- токен
значение-директивы    <- ( токен S )*
значение              <- примитив / код-блок

; --- Префиксы ---
префикс-комментария <- "---" / "--?" / "--!" / "--/"
префикс-директивы   <- "!"
префикс-объекта     <- ":"
префикс-массива     <- ".."
префикс-примитива   <- "."

; --- Базовые определения ---
отступ            <- [ " " ]+
токен             <- ( !"--" !S . )+
строка-в-кавычках <- "\"" [^"]* "\"" / "'" [^']* "'" / "(" [^)]* ")"
число             <- "-"? [0-9]+ ("." [0-9]+)? ([eE] "-"? [0-9]+)?
булево            <- "true" / "false" / "yes" / "no" / "да" / "нет"
null              <- "null"

; --- Фрагмент кода ---
код-блок          <- код-блок-3 / код-блок-1
код-блок-3        <- "```" [^\n]* CRLF ( !"```" . )* "```"
код-блок-1        <- "`" [^\n]* CRLF ( !( CRLF [ \t]* "`" ) . )* CRLF [ \t]* "`"

S                 <- [ \t\n\r]
CRLF              <- [\n\r]
````

## Реализация

### Запуск

Приложение статическое: сборки нет, зависимостей нет. Достаточно раздать
каталог `src/` любым HTTP-сервером. Открывать `src/index.html` двойным
щелчком нельзя — редактор целиком на ES-модулях, а с `file://` браузер их
не загружает.

```powershell
python -m http.server 8000 --directory src
# затем http://localhost:8000/
```

### Тесты

Раннеры на Python (только стандартная библиотека), браузерные проверки — в
headless Chrome/Edge. Node не нужен.

```powershell
python tests/lexer/run_tests.py       # 45 golden-кейсов лексера/парсера
python tests/features/run_tests.py    # подстановка, код-блоки, новая строка, подсветка
python tests/security/run_tests.py    # регрессии безопасности (экранирование)
python tests/files/run_tests.py       # localStorage и экспорт/импорт файлов
python tests/converters/run_tests.py  # smoke: json, xml, proto, ui, bpmn, форма
python tests/flexforms/run_tests.py   # флейвор «форма-ТСД»
```

У `tests/flexforms` внешних зависимостей нет: только Python 3 и Chrome/Edge для
браузерного дыма. Генерация ассетов из внешнего `редизайн/`, сравнение с ним и
JS-прогоны через `quickjs` удалены — проект и тесты живут на чистом JS и
стандартной библиотеке Python.
